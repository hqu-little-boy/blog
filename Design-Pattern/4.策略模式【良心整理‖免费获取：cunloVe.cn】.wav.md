# 策略模式（Strategy Pattern）

## 一、动机

在软件构建过程中，某些对象可能使用多种不同的算法（广义的算法，包括业务规则、计算方式等），且这些算法经常变化。如果将所有算法都硬编码到对象内部，会带来两个问题：

1. **对象变得非常复杂**——大量条件分支混杂在一起
2. **性能负担**——不常使用的算法也被装载到内存/代码段中，占用缓存空间

策略模式正是为了解决这类问题而存在的。

---

## 二、问题场景：跨国税务计算

假设有一个电子商务系统，需要根据不同的国家计算订单税款。目前需支持中国、美国、德国三国税法，未来可能扩展到更多国家。

### 2.1 反面示例：枚举 + if-else

```cpp
#include <iostream>
#include <stdexcept>

enum TaxRegion { CN, US, DE };

class SalesOrder {
public:
    SalesOrder(TaxRegion region, double amount)
        : region_(region), amount_(amount) {}

    double calculateTax() const {
        if (region_ == CN) {
            return amount_ * 0.13;  // 中国增值税 13%
        } else if (region_ == US) {
            return amount_ * 0.08;  // 美国综合销售税约 8%
        } else if (region_ == DE) {
            return amount_ * 0.19;  // 德国增值税 19%
        }
        // 若需支持法国，必须在此添加 else if 分支
        throw std::runtime_error("Unsupported region");
    }

private:
    TaxRegion region_;
    double amount_;
};

int main() {
    SalesOrder cnOrder(CN, 1000.0);
    SalesOrder usOrder(US, 1000.0);
    SalesOrder deOrder(DE, 1000.0);

    std::cout << "CN tax: " << cnOrder.calculateTax() << std::endl;  // 130
    std::cout << "US tax: " << usOrder.calculateTax() << std::endl;  // 80
    std::cout << "DE tax: " << deOrder.calculateTax() << std::endl;  // 190
    return 0;
}
```

这种写法初看没有问题，算法正确即可。但加入**时间轴**来考虑未来的变化：

- 若需支持法国，必须修改枚举类型（新增 `FR`）并在 `calculateTax()` 中添加新的 `else if` 分支
- 这是对**已有代码的修改**，而非扩展

**违背了开闭原则（Open-Closed Principle）**：类模块应该对扩展开放、对更改封闭。

---

## 三、策略模式的解决方案

将每个算法封装为独立的类，通过多态实现运行时的灵活切换。

### 3.1 UML 类图结构

```
┌───────────────────┐         ┌─────────────────────┐
│    Context         │         │   Strategy (抽象基类) │
│   (SalesOrder)     │────────>│   + calculate(): double │
│                    │         └──────────┬──────────┘
└───────────────────┘                    │
                            ┌────────────┼────────────┐
                            │            │            │
                     ┌──────┴───┐  ┌─────┴────┐  ┌───┴──────┐
                     │ CNTax    │  │ USTax    │  │ DETax    │
                     │          │  │          │  │          │
                     └──────────┘  └──────────┘  └──────────┘
```

- **红色（稳定部分）**：`Strategy` 基类 + `Context`（SalesOrder）
- **蓝色（变化部分）**：各 `ConcreteStrategy` 子类

### 3.2 代码实现

```cpp
#include <iostream>
#include <memory>
#include <stdexcept>

// ============================================================
// Strategy 抽象基类：定义税法计算的统一接口
// ============================================================
class TaxStrategy {
public:
    virtual ~TaxStrategy() = default;               // 基类必须声明虚析构函数
    virtual double calculate(double amount) const = 0;  // 纯虚函数
};

// ============================================================
// ConcreteStrategy：中国税法
// ============================================================
class CNTax : public TaxStrategy {
public:
    double calculate(double amount) const override {
        return amount * 0.13;  // 增值税 13%
    }
};

// ============================================================
// ConcreteStrategy：美国税法
// ============================================================
class USTax : public TaxStrategy {
public:
    double calculate(double amount) const override {
        return amount * 0.08;  // 综合销售税约 8%
    }
};

// ============================================================
// ConcreteStrategy：德国税法
// ============================================================
class DETax : public TaxStrategy {
public:
    double calculate(double amount) const override {
        return amount * 0.19;  // 增值税 19%
    }
};

// ============================================================
// Context：销售订单，持有一个 TaxStrategy 多态指针
// ============================================================
class SalesOrder {
public:
    // 通过构造函数注入具体策略（实际项目中可由工厂模式创建）
    explicit SalesOrder(std::unique_ptr<TaxStrategy> strategy, double amount)
        : strategy_(std::move(strategy)), amount_(amount) {}

    double calculateTax() const {
        // 多态调用 —— 运行时根据实际策略对象决定调用哪个算法
        return strategy_->calculate(amount_);
    }

private:
    std::unique_ptr<TaxStrategy> strategy_;
    double amount_;
};

int main() {
    SalesOrder cnOrder(std::make_unique<CNTax>(), 1000.0);
    SalesOrder usOrder(std::make_unique<USTax>(), 1000.0);
    SalesOrder deOrder(std::make_unique<DETax>(), 1000.0);

    std::cout << "CN tax: " << cnOrder.calculateTax() << std::endl;  // 130
    std::cout << "US tax: " << usOrder.calculateTax() << std::endl;  // 80
    std::cout << "DE tax: " << deOrder.calculateTax() << std::endl;  // 190
    return 0;
}
```

### 3.3 扩展时的对比

| 对比维度 | 枚举 + if-else | 策略模式 |
|---------|--------------|---------|
| 新增法国税法 | 修改枚举 + 修改 `calculateTax()` | 新增 `FRTax` 类即可 |
| 是否修改已有代码 | 是 | 否 |
| 是否遵循开闭原则 | 否 | 是 |
| 复用性 | 源码级粘贴（非真正复用） | 二进制级复用 |

扩展法国税法只需：

```cpp
class FRTax : public TaxStrategy {
public:
    double calculate(double amount) const override {
        return amount * 0.20;  // 法国增值税 20%
    }
};
```

`SalesOrder` 类**完全不需要修改**。

## 四、核心设计原则

### 4.1 开闭原则（Open-Closed Principle）

> 对扩展开放，对更改封闭。类模块应该尽可能用扩展的方式来支持未来的变化，而不是修改已有源代码。

策略模式是开闭原则的典型体现：新增算法通过添加新类（扩展），而非修改已有代码（更改）。

### 4.2 复用性的真正含义

侯捷老师特别强调：

- **源代码级的复制粘贴不是复用**——那只是拷贝源代码片段
- **真正的复用是二进制层面的**——编译、测试、部署后，原封不动地被其他模块使用
- 在已有方法后面追加代码，实践中很可能引入 bug 到前面的代码中

### 4.3 识别策略模式的信号

当代码中出现大量 `if-else` 或 `switch-case` 条件分支时，应考虑策略模式：

- 如果这些条件分支**可能在未来增加新的情况**（如新增国家、新增支付方式等），则适合使用策略模式
- 如果条件是**绝对稳定不变的**（如一周七天），则可以使用 `if-else`

用 Martin Fowler 的话来说，大量的 `if-else` 是代码中的 **bad smell（坏味道）**，约 80%~90% 的情况下都值得考虑用策略模式重构。

## 五、策略模式的定义（GoF）

> 定义一系列算法，把它们一个个封装起来，并且使它们可以互相替换（支持变化）。该模式使得算法可以独立于使用它的客户而变化（稳定）。

关键词解析：
- **封装**：每个算法被封装为独立的类
- **互相替换**：通过多态，在运行时灵活切换算法
- **独立变化**：算法的变化不会影响使用算法的 Context（如 SalesOrder）

---

## 六、运行时多态

策略模式的关键在于**运行时**的多态调用：

```cpp
double calculateTax() const {
    return strategy_->calculate(amount_);  // 运行时多态调用
}
```

`strategy_` 是一个基类指针，指向的具体子类对象在运行时确定，因此调用的算法也在运行时决定。这正是面向对象多态的威力。

---

## 七、策略模式与工厂模式的配合

在实际项目中，策略对象通常不直接在 Context 中硬编码 `new`，而是通过**工厂模式**创建：

```cpp
// 伪代码示意
class TaxStrategyFactory {
public:
    static std::unique_ptr<TaxStrategy> create(const std::string& region) {
        if (region == "CN") return std::make_unique<CNTax>();
        if (region == "US") return std::make_unique<USTax>();
        if (region == "DE") return std::make_unique<DETax>();
        throw std::runtime_error("Unknown region");
    }
};

// 使用
auto strategy = TaxStrategyFactory::create("CN");
SalesOrder order(std::move(strategy), 1000.0);
```

这样 SalesOrder 的创建过程也保持了灵活性。

---

## 八、策略对象的共享

如果 Strategy 对象没有实例变量（即所有状态都通过参数传入），那么多个 Context 可以共享同一个 Strategy 对象，节省内存开销。此时 Strategy 对象甚至可以设计为单例（Singleton）。

```cpp
// 无状态的策略对象可以共享
class CNTax : public TaxStrategy {
public:
    double calculate(double amount) const override {
        return amount * 0.13;  // 无成员变量，可安全共享
    }
};

// 多个 SalesOrder 可共享同一个 CNTax 实例
static CNTax sharedCNTax;
SalesOrder order1(&sharedCNTax, 1000.0);
SalesOrder order2(&sharedCNTax, 2000.0);
```

## 九、策略模式的性能优势（附带好处）

使用策略模式还有附带的性能好处：

- **代码本地性（Locality）**：运行时只加载实际使用的策略类的代码，不会把所有分支的代码都装载进 CPU 高速缓存
- if-else 方式下，所有分支代码都会被装载到代码段中，可能挤占缓存空间，导致其他代码被挤出缓存甚至落入虚拟内存（硬盘）
- 策略模式下，执行时直接跳转到具体策略方法，代码段更紧凑，缓存利用率更高

> 注意：这不是策略模式的主要价值，而是顺带的好处。

## 十、总结

| 要点 | 说明 |
|------|------|
| 本质 | 将算法封装为对象，通过多态实现运行时切换 |
| 核心原则 | 开闭原则（对扩展开放，对更改封闭） |
| 稳定部分 | Strategy 基类 + Context |
| 变化部分 | 各 ConcreteStrategy 子类 |
| 识别信号 | 代码中出现大量可能扩展的 if-else / switch-case |
| 适用场景 | 算法/策略/规则经常变化的业务场景 |
| 关键词 | 运行时多态、二进制复用、扩展而非修改 |
