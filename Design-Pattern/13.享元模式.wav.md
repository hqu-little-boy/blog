# 享元模式（Flyweight Pattern）

## 一、模式概述

享元模式是一种**结构型设计模式**，其核心思想是：**通过共享技术来有效地支持大量细粒度的对象**，从而避免因对象数量过多而导致的内存和性能开销。

在面向对象设计中，"一切皆对象"的理念在某些场景下会产生问题——当系统中存在大量细粒度对象时（几万甚至几十万个），对象本身的内存开销会成为显著的性能瓶颈。享元模式正是为解决这一问题而生。

> 在整个设计模式体系中，只有**享元模式**和**单例模式**解决的不是抽象性问题，而是**性能/代价问题**。

---

## 二、核心思想

### 2.1 共享机制

享元模式的核心是**对象池 + 查找复用**：

1. 用一个**工厂**（Factory）管理对象的创建
2. 工厂内部维护一个**对象池**（通常使用 `std::unordered_map` 或 `std::map`）
3. 每个对象以一个**唯一的 key** 标识
4. 请求创建对象时：
   - 如果 key 在池中**已存在** → 直接返回已有对象（复用）
   - 如果 key **不存在** → 创建新对象，加入池中，然后返回

```
getFlyweight(key):
    if key in pool:
        return pool[key]          // 复用
    else:
        obj = new Flyweight(key)
        pool[key] = obj
        return obj                // 创建并缓存
```

### 2.2 内部状态与外部状态

享元模式将对象的状态分为两类：

| 状态类型 | 说明 | 是否可共享 | 示例 |
|---------|------|-----------|------|
| **内部状态**（Intrinsic） | 存储在享元对象中，不随环境改变 | 可共享 | 字体名称、颜色、纹理 |
| **外部状态**（Extrinsic） | 由客户端维护，随环境变化 | 不可共享 | 字符在文档中的位置 (x, y) |

### 2.3 不可变性要求

享元对象一旦创建，其状态**不应被修改**（只读/不可变）。原因显而易见：如果共享的对象被某处修改，所有引用该对象的地方都会受到影响，导致数据不一致。

> Java 和 C# 中的 `String` 类型就是不可变的，这使得字符串池（String Pool）的共享机制得以安全运行。C++ 标准库中的 `std::string` 是可变的，但通过写时复制（Copy-on-Write）等技术来优化。

## 三、UML 结构

```
┌─────────────────────┐        ┌──────────────────────────┐
│   FlyweightFactory  │        │       Flyweight          │
│─────────────────────│        │──────────────────────────│
│ - pool: Map<Key,F>  │───────>│ + operation(extrinsic)   │
│─────────────────────│        │                          │
│ + getFlyweight(key) │        │  (存储内部状态)           │
└─────────────────────┘        └──────────────────────────┘
         ▲                              ▲
         │                              │
         │                              │
┌─────────────────────┐        ┌──────────────────────────┐
│     Client          │───────>│  ConcreteFlyweight       │
│ (持有外部状态)        │        │  (具体享元实现)           │
└─────────────────────┘        └──────────────────────────┘
```

## 四、适用场景

- 系统中有**大量相似对象**，且这些对象的大部分状态可以外部化
- 对象的**创建开销大**，或者占用**大量内存**
- 对象的**内部状态可以与外部状态分离**
- 需要**减少对象数量**以降低内存占用或提升性能
- 典型应用：字符串池、线程池、连接池、编辑器中的字符/字体管理、游戏中的粒子/树木渲染

## 五、代码示例

### 5.1 示例一：字体工厂（对应课程讲解）

```cpp
#include <iostream>
#include <string>
#include <unordered_map>
#include <memory>

// 享元对象：字体
class Font {
private:
    std::string key_;
    std::string family_;
    int size_;
public:
    Font(const std::string& key) : key_(key), family_(key), size_(12) {
        std::cout << "  [创建] Font: " << key_ << std::endl;
    }
    void display(const std::string& text) const {
        std::cout << "  [渲染] \"" << text << "\" 字体=" << family_ << std::endl;
    }
    const std::string& getKey() const { return key_; }
};

// 享元工厂：字体工厂（对象池）
class FontFactory {
private:
    std::unordered_map<std::string, std::shared_ptr<Font>> pool_;
public:
    std::shared_ptr<Font> getFont(const std::string& key) {
        auto it = pool_.find(key);
        if (it != pool_.end()) {
            std::cout << "  [复用] Font: " << key << std::endl;
            return it->second;
        }
        auto font = std::make_shared<Font>(key);
        pool_[key] = font;
        return font;
    }
    size_t poolSize() const { return pool_.size(); }
};

int main() {
    FontFactory factory;

    auto f1 = factory.getFont("Arial");
    auto f2 = factory.getFont("Times New Roman");
    auto f3 = factory.getFont("Arial");           // 复用
    auto f4 = factory.getFont("Courier New");
    auto f5 = factory.getFont("Times New Roman");  // 复用

    f1->display("Hello");
    f3->display("Flyweight");

    std::cout << "获取5次，实际创建: " << factory.poolSize() << " 个字体对象" << std::endl;
    // 输出: 获取5次，实际创建: 3 个字体对象
    return 0;
}
```

**运行输出：**
```
  [创建] Font: Arial
  [创建] Font: Times New Roman
  [复用] Font: Arial
  [创建] Font: Courier New
  [复用] Font: Times New Roman
  [渲染] "Hello" 字体=Arial
  [渲染] "Flyweight" 字体=Arial
获取5次，实际创建: 3 个字体对象
```

> 课程要点：十页文档中实际使用的字体不过四五种、七八种，但字符可能有几十万个。如果不使用享元模式，每个字符创建一个字体对象，系统将难以承受。

### 5.2 示例二：森林树木（经典设计模式示例）

```cpp
#include <iostream>
#include <string>
#include <unordered_map>
#include <vector>
#include <memory>

// 享元对象：树的类型（内部状态 —— 名称、颜色、纹理）
class TreeType {
private:
    std::string name_, color_, texture_;
public:
    TreeType(const std::string& n, const std::string& c, const std::string& t)
        : name_(n), color_(c), texture_(t) {}
    void draw(int x, int y) const {
        std::cout << "  绘制 [" << name_ << "] 颜色=" << color_
                  << " 位置=(" << x << "," << y << ")" << std::endl;
    }
};

// 享元工厂
class TreeTypeFactory {
private:
    static std::unordered_map<std::string, std::shared_ptr<TreeType>> pool_;
public:
    static std::shared_ptr<TreeType> get(const std::string& n,
                                          const std::string& c,
                                          const std::string& t) {
        std::string key = n + "|" + c + "|" + t;
        auto it = pool_.find(key);
        if (it != pool_.end()) return it->second;
        auto type = std::make_shared<TreeType>(n, c, t);
        pool_[key] = type;
        return type;
    }
    static size_t poolSize() { return pool_.size(); }
};
std::unordered_map<std::string, std::shared_ptr<TreeType>> TreeTypeFactory::pool_;

// 非享元部分：每棵树的位置（外部状态）
class Tree {
    int x_, y_;
    std::shared_ptr<TreeType> type_;
public:
    Tree(int x, int y, std::shared_ptr<TreeType> t) : x_(x), y_(y), type_(t) {}
    void draw() const { type_->draw(x_, y_); }
};

// 森林：管理大量树木
class Forest {
    std::vector<std::unique_ptr<Tree>> trees_;
public:
    void plant(int x, int y, const std::string& n, const std::string& c, const std::string& t) {
        trees_.push_back(std::make_unique<Tree>(x, y, TreeTypeFactory::get(n, c, t)));
    }
    void draw() const { for (auto& t : trees_) t->draw(); }
    size_t count() const { return trees_.size(); }
};

int main() {
    Forest forest;
    forest.plant(10, 20, "橡树", "绿", "粗糙");
    forest.plant(30, 40, "松树", "深绿", "光滑");
    forest.plant(50, 60, "橡树", "绿", "粗糙");   // 复用
    forest.plant(70, 80, "松树", "深绿", "光滑");  // 复用
    forest.plant(90, 10, "橡树", "绿", "粗糙");   // 复用
    forest.plant(15, 25, "柳树", "浅绿", "柔滑");

    forest.draw();
    std::cout << "树木总数: " << forest.count()
              << ", 共享类型数: " << TreeTypeFactory::poolSize()
              << ", 节省: " << forest.count() - TreeTypeFactory::poolSize()
              << " 个对象" << std::endl;
    return 0;
}
```

**运行输出：**
```
  绘制 [橡树] 颜色=绿 位置=(10,20)
  绘制 [松树] 颜色=深绿 位置=(30,40)
  绘制 [橡树] 颜色=绿 位置=(50,60)
  绘制 [松树] 颜色=深绿 位置=(70,80)
  绘制 [橡树] 颜色=绿 位置=(90,10)
  绘制 [柳树] 颜色=浅绿 位置=(15,25)
树木总数: 6, 共享类型数: 3, 节省: 3 个对象
```

### 5.3 示例三：内部状态与外部状态分离

```cpp
#include <iostream>
#include <string>
#include <unordered_map>
#include <memory>

// 享元对象：字符样式（内部状态 —— 字体、字号、颜色）
// 注意：没有 setter，对象创建后不可变
class CharStyle {
    std::string font_; int size_; std::string color_;
public:
    CharStyle(const std::string& f, int s, const std::string& c)
        : font_(f), size_(s), color_(c) {}
    void render(int x, int y, char ch) const {
        std::cout << "  '" << ch << "' (" << x << "," << y << ") "
                  << font_ << "/" << size_ << "/" << color_ << std::endl;
    }
};

// 享元工厂
class StyleFactory {
    static std::unordered_map<std::string, std::shared_ptr<CharStyle>> pool_;
public:
    static std::shared_ptr<CharStyle> get(const std::string& f, int s, const std::string& c) {
        std::string key = f + "|" + std::to_string(s) + "|" + c;
        auto it = pool_.find(key);
        if (it != pool_.end()) return it->second;
        auto style = std::make_shared<CharStyle>(f, s, c);
        pool_[key] = style;
        return style;
    }
    static size_t poolSize() { return pool_.size(); }
};
std::unordered_map<std::string, std::shared_ptr<CharStyle>> StyleFactory::pool_;

int main() {
    // 外部状态：每个字符的位置不同，不可共享
    struct Ex { int x, y; char ch; std::shared_ptr<CharStyle> s; };
    Ex text[] = {
        {0,0,'H', StyleFactory::get("Arial",12,"黑")},
        {1,0,'e', StyleFactory::get("Arial",12,"黑")},
        {2,0,'l', StyleFactory::get("Arial",12,"黑")},
        {3,0,'l', StyleFactory::get("Arial",12,"黑")},
        {4,0,'o', StyleFactory::get("Arial",12,"黑")},
        {6,0,'W', StyleFactory::get("Times",14,"红")},
        {7,0,'o', StyleFactory::get("Times",14,"红")},
        {8,0,'r', StyleFactory::get("Times",14,"红")},
        {9,0,'l', StyleFactory::get("Times",14,"红")},
        {10,0,'d', StyleFactory::get("Times",14,"红")},
    };
    for (auto& c : text) c.s->render(c.x, c.y, c.ch);

    int total = sizeof(text) / sizeof(text[0]);
    std::cout << "字符数: " << total
              << ", 共享样式: " << StyleFactory::poolSize() << std::endl;
    // 输出: 字符数: 10, 共享样式: 2
    return 0;
}
```

## 六、对象内存开销评估

课程中提到了如何评估对象是否需要使用享元模式。以下是关键的评估方法：

### 6.1 单个对象的大小计算

```cpp
#include <iostream>

struct MyObject {
    int a;          // 4 bytes
    double b;       // 8 bytes
    int c;          // 4 bytes
    virtual void foo() {}  // 虚函数表指针: 4 bytes (32位) / 8 bytes (64位)
};

int main() {
    std::cout << "sizeof(MyObject) = " << sizeof(MyObject) << " bytes" << std::endl;
    // 64位系统典型输出: 32 bytes（含对齐填充和 vptr）
    return 0;
}
```

对象大小 = **字段大小之和** + **字节对齐填充** + **虚函数表指针**（如有虚函数）

### 6.2 总内存估算

以课程中的例子（10 个 int 字段的对象，32 位平台）：

| 对象数量 | 单个对象大小 | 总内存 | 评估 |
|---------|------------|--------|------|
| 1,000 | ~40 bytes | ~40 KB | 可忽略 |
| 10,000 | ~40 bytes | ~400 KB | 可接受 |
| 100,000 | ~40 bytes | ~4 MB | 相当可观 |
| 1,000,000 | ~40 bytes | ~40 MB | 需要考虑优化 |

> **经验值**：常见客户端进程内存在 5~10 MB 左右，上 100 MB 的进程很少。当单类对象占用内存达到兆级别时，应考虑使用享元模式。
>
> 注意：享元模式本身的数据结构（如 `unordered_map`）也有额外开销，不要对几十个对象就使用享元模式，否则得不偿失。

## 七、相关设计模式对比

| 模式 | 关注点 | 说明 |
|------|--------|------|
| **享元模式** | 性能/内存 | 通过共享减少对象数量 |
| **单例模式** | 性能/资源 | 保证全局唯一实例 |
| **代理模式** | 透明访问 | C++ `std::string` 曾用代理模式实现写时复制（COW） |
| **工厂模式** | 对象创建 | 享元工厂本质上也是一种工厂 |

## 八、语言层面的享元机制

享元思想不仅体现在设计模式中，许多语言在**编译器/运行时层面**已经内置了享元机制：

| 语言 | 机制 | 说明 |
|------|------|------|
| **Java** | 字符串池（String Pool） | 编译期/运行时自动对字符串字面量进行享元 |
| **C#** | 字符串驻留（String Interning） | 类似 Java，编译器层面自动共享 |
| **Swift** | Copy-on-Write | 对值类型采用写时复制优化 |
| **C++ STL** | 部分实现使用 COW | `std::string` 在某些实现中使用代理模式实现写时复制 |

## 九、总结

1. **享元模式的本质**：用共享的方式支持大量细粒度对象，降低内存开销
2. **关键要素**：对象池 + 唯一 key + 内部/外部状态分离 + 不可变性
3. **使用前提**：必须经过实际评估，确认对象数量确实带来了可观的内存负担
4. **实现灵活**：数据结构、接口设计、key 的表达方式等均可根据场景调整
5. **代价**：享元模式本身引入了工厂和数据结构的额外开销，需要权衡
