# 访问器模式（Visitor Pattern）

## 一、问题引入

在软件构建过程中，有时需求的变化会导致**类层次结构**需要添加某些新的行为。

### 场景描述

假设有一个类层次结构：

```
Element（基类）
├── ElementA（子类A）
├── ElementB（子类B）
└── ...（其他子类）
```

基类 `Element` 已经有一些操作函数。现在需求变更，需要给整个类层次结构添加新的操作（如 `Func2`）。

### 直观但有问题的做法

最直观的方式是在基类 `Element` 中添加新的虚函数，然后在每个子类中 override：

```cpp
class Element {
public:
    virtual void Func1() = 0;
    virtual void Func2(/* 参数 */) = 0;  // 新增
};

class ElementA : public Element {
public:
    void Func1() override { /* ... */ }
    void Func2(/* 参数 */) override { /* ElementA 的实现 */ }
};

class ElementB : public Element {
public:
    void Func1() override { /* ... */ }
    void Func2(/* 参数 */) override { /* ElementB 的实现 */ }
};
```

### 这种做法的问题

- **违反开闭原则（Open-Closed Principle, OCP）**：不鼓励在需求变更时修改源代码，尤其是已经开发完成、部署之后的代码。
- **变更负担重**：基类一改，由于是虚函数，所有子类都必须为此更改。
- **不灵活**：如果过一段时间用户又需要加 `Func3`、`Func4`……这种方式就招架不住了。

> **开闭原则**：对扩展开放，对修改关闭。不更改源代码，而是通过扩展来应对新的需求变化。

## 二、Visitor 模式概述

### 核心思想

Visitor 模式表示一个**作用于某对象结构中各个元素的操作**。它使得可以在**不改变各个元素的类的前提下**，定义作用于这些元素的新操作。

### 前提条件

- **能预料到**未来可能需要为整个类层次结构添加新的操作
- **不知道**具体要添加多少个操作、添加什么操作
- 需要预先做一个设计（在 `Element` 中添加 `accept` 虚函数）

---

## 三、模式结构

### UML 类图

```
          ┌─────────────┐
          │   Visitor    │  （抽象访问者）
          ├─────────────┤
          │ visit(ElementA) │
          │ visit(ElementB) │
          └──────┬──────┘
                 │
        ┌────────┴────────┐
        │                 │
┌───────┴───────┐ ┌───────┴───────┐
│ ConcreteVisitor1│ │ ConcreteVisitor2│  （具体访问者，新增操作）
├───────────────┤ ├───────────────┤
│ visit(ElementA) │ │ visit(ElementA) │
│ visit(ElementB) │ │ visit(ElementB) │
└───────────────┘ └───────────────┘

          ┌─────────────┐
          │   Element    │  （抽象元素）
          ├─────────────┤
          │ accept(Visitor)│ ◄──────── 虚函数，关键接口
          └──────┬──────┘
                 │
        ┌────────┴────────┐
        │                 │
┌───────┴───────┐ ┌───────┴───────┐
│  ElementA      │ │  ElementB      │  （具体元素）
├───────────────┤ ├───────────────┤
│ accept(Visitor) │ │ accept(Visitor) │
│   → v.visit(*this)│ │   → v.visit(*this)│
└───────────────┘ └───────────────┘
```

### 角色说明

| 角色 | 说明 |
|------|------|
| **Visitor**（抽象访问者） | 为每一个具体元素类声明一个 `visit` 操作 |
| **ConcreteVisitor**（具体访问者） | 实现 `Visitor` 中声明的操作，每个操作实现对相应元素的一部分操作 |
| **Element**（抽象元素） | 声明一个 `accept` 操作，以一个访问者为参数 |
| **ConcreteElement**（具体元素） | 实现 `accept` 操作，在其中调用访问者的 `visit` 方法 |
| **ObjectStructure**（对象结构） | 可以枚举它的元素，提供一个高层接口允许访问者访问它的元素 |

## 四、Double Dispatch（双重分发/二次多态辨析）

这是 Visitor 模式中**最核心的机制**，需要深刻理解。

### 执行过程

以 `element->accept(visitor)` 为例：

```
第一次多态辨析（Dispatch 1）：
  element->accept(visitor)
  ↓ 由于 accept 是虚函数，根据 element 的实际运行时类型分发
  ↓ 假设 element 的实际类型是 ElementB
  → 调用 ElementB::accept(visitor)

第二次多态辨析（Dispatch 2）：
  ElementB::accept(visitor) 内部调用 visitor.visit(*this)
  ↓ 由于 visit 是虚函数，根据 visitor 的实际运行时类型分发
  ↓ 假设 visitor 的实际类型是 Visitor2
  → 调用 Visitor2::visit(ElementB&)
```

### 为什么要传引用/指针

传引用（或指针）才能保留多态信息。如果传值，会发生对象切片，丢失运行时类型信息，第二次分发就无法正确进行。

## 五、示例代码

### 示例 1：不使用 Visitor 模式（违反开闭原则）

```cpp
#include <iostream>
#include <vector>
#include <memory>

namespace WithoutVisitor {

class Shape {
public:
    virtual ~Shape() = default;
    virtual void draw() const = 0;
    // 每次新增操作都要修改基类，违反开闭原则
    // virtual void serialize() = 0;
    // virtual void exportToPDF() = 0;
};

class Circle : public Shape {
public:
    void draw() const override {
        std::cout << "Drawing Circle" << std::endl;
    }
};

class Rectangle : public Shape {
public:
    void draw() const override {
        std::cout << "Drawing Rectangle" << std::endl;
    }
};

class Line : public Shape {
public:
    void draw() const override {
        std::cout << "Drawing Line" << std::endl;
    }
};

} // namespace WithoutVisitor
```

**问题**：每次添加新操作（如 `serialize`、`exportToPDF`），都要修改 `Shape` 基类及所有子类。

### 示例 2：使用 Visitor 模式（遵循开闭原则）

```cpp
#include <iostream>
#include <vector>
#include <memory>

namespace WithVisitor {

// 前向声明
class Circle;
class Rectangle;
class Line;

// Visitor 基类：针对每个具体元素类声明一个 visit 方法
class ShapeVisitor {
public:
    virtual ~ShapeVisitor() = default;
    virtual void visit(Circle& c) = 0;
    virtual void visit(Rectangle& r) = 0;
    virtual void visit(Line& l) = 0;
};

// Element 基类：声明 accept 接口
class Shape {
public:
    virtual ~Shape() = default;
    virtual void draw() const = 0;
    virtual void accept(ShapeVisitor& visitor) = 0;  // 关键：接受 Visitor
};

// ConcreteElement：Circle
class Circle : public Shape {
public:
    void draw() const override {
        std::cout << "Drawing Circle" << std::endl;
    }
    void accept(ShapeVisitor& visitor) override {
        visitor.visit(*this);  // 第一次多态辨析
    }
};

// ConcreteElement：Rectangle
class Rectangle : public Shape {
public:
    void draw() const override {
        std::cout << "Drawing Rectangle" << std::endl;
    }
    void accept(ShapeVisitor& visitor) override {
        visitor.visit(*this);  // 第一次多态辨析
    }
};

// ConcreteElement：Line
class Line : public Shape {
public:
    void draw() const override {
        std::cout << "Drawing Line" << std::endl;
    }
    void accept(ShapeVisitor& visitor) override {
        visitor.visit(*this);  // 第一次多态辨析
    }
};

// ============================================================
// 以下为"未来"动态添加的新操作（通过扩展而非修改）
// ============================================================

// 新操作 1：序列化
class SerializationVisitor : public ShapeVisitor {
public:
    void visit(Circle&) override {
        std::cout << "Serializing Circle: {type:\"circle\"}" << std::endl;
    }
    void visit(Rectangle&) override {
        std::cout << "Serializing Rectangle: {type:\"rectangle\"}" << std::endl;
    }
    void visit(Line&) override {
        std::cout << "Serializing Line: {type:\"line\"}" << std::endl;
    }
};

// 新操作 2：计算面积
class AreaCalculatorVisitor : public ShapeVisitor {
public:
    void visit(Circle&) override {
        std::cout << "Calculating area of Circle: pi * r^2" << std::endl;
    }
    void visit(Rectangle&) override {
        std::cout << "Calculating area of Rectangle: width * height" << std::endl;
    }
    void visit(Line&) override {
        std::cout << "Calculating area of Line: 0 (line has no area)" << std::endl;
    }
};

// 新操作 3：导出为 SVG
class SVGExportVisitor : public ShapeVisitor {
public:
    void visit(Circle&) override {
        std::cout << "Exporting Circle to SVG: <circle/>" << std::endl;
    }
    void visit(Rectangle&) override {
        std::cout << "Exporting Rectangle to SVG: <rect/>" << std::endl;
    }
    void visit(Line&) override {
        std::cout << "Exporting Line to SVG: <line/>" << std::endl;
    }
};

} // namespace WithVisitor
```

**使用方式**：

```cpp
int main() {
    using namespace WithVisitor;

    std::vector<std::unique_ptr<Shape>> shapes;
    shapes.push_back(std::make_unique<Circle>());
    shapes.push_back(std::make_unique<Rectangle>());
    shapes.push_back(std::make_unique<Line>());

    // 新操作 1：序列化 —— 无需修改 Element 类层次结构
    SerializationVisitor serializer;
    for (auto& s : shapes) {
        s->accept(serializer);
    }

    // 新操作 2：计算面积
    AreaCalculatorVisitor areaCalc;
    for (auto& s : shapes) {
        s->accept(areaCalc);
    }

    // 新操作 3：导出 SVG
    SVGExportVisitor svgExporter;
    for (auto& s : shapes) {
        s->accept(svgExporter);
    }

    return 0;
}
```

### 示例 3：Double Dispatch 双重分发演示

```cpp
#include <iostream>

namespace DoubleDispatchDemo {

class ElementB;  // 前向声明

// Visitor 基类
class Visitor {
public:
    virtual ~Visitor() = default;
    virtual void visitElementA() = 0;
    virtual void visitElementB(ElementB& b) = 0;
};

// Element 基类
class Element {
public:
    virtual ~Element() = default;
    virtual void accept(Visitor& v) = 0;
};

// ConcreteElementA
class ElementA : public Element {
public:
    void accept(Visitor& v) override {
        std::cout << "[ElementA::accept] 第一次多态辨析" << std::endl;
        v.visitElementA();  // 第一次 Dispatch
    }
};

// ConcreteElementB
class ElementB : public Element {
public:
    void accept(Visitor& v) override {
        std::cout << "[ElementB::accept] 第一次多态辨析" << std::endl;
        v.visitElementB(*this);  // 第一次 Dispatch
    }
};

// ConcreteVisitor2
class Visitor2 : public Visitor {
public:
    void visitElementA() override {
        std::cout << "[Visitor2::visitElementA] 第二次多态辨析" << std::endl;
    }
    void visitElementB(ElementB&) override {
        std::cout << "[Visitor2::visitElementB] 第二次多态辨析" << std::endl;
    }
};

} // namespace DoubleDispatchDemo

int main() {
    using namespace DoubleDispatchDemo;

    Visitor2 visitor;

    std::cout << "--- ElementA.accept(visitor) ---" << std::endl;
    ElementA a;
    a.accept(visitor);
    // 输出:
    // [ElementA::accept] 第一次多态辨析
    // [Visitor2::visitElementA] 第二次多态辨析

    std::cout << "\n--- ElementB.accept(visitor) ---" << std::endl;
    ElementB b;
    b.accept(visitor);
    // 输出:
    // [ElementB::accept] 第一次多态辨析
    // [Visitor2::visitElementB] 第二次多态辨析

    return 0;
}
```

## 六、模式优缺点分析

### 稳定的部分（不应改变）

```
┌─────────────────────────────────────────┐
│  Visitor（抽象访问者）                    │  ← 稳定
│  Element（抽象元素）                      │  ← 稳定
│  ElementA, ElementB, ...（所有具体元素）  │  ← 稳定
│  accept() 函数                           │  ← 稳定
└─────────────────────────────────────────┘
```

**关键前提**：`Element` 的所有子类（`ElementA`、`ElementB`……）必须是**确定的、稳定的**。因为 `Visitor` 基类中需要为每一个具体元素类声明一个 `visit` 方法。

### 变化的部分（可扩展）

```
┌─────────────────────────────────────────┐
│  ConcreteVisitor1, ConcreteVisitor2, ... │  ← 可扩展
│  （新增的操作通过继承 Visitor 实现）       │
└─────────────────────────────────────────┘
```

每次需要添加新操作时，只需继承 `Visitor`，实现一个新的 `ConcreteVisitor`，无需修改 `Element` 类层次结构中的任何代码。

### 优点

| 优点 | 说明 |
|------|------|
| 遵循开闭原则 | 新增操作通过扩展（新增 `ConcreteVisitor`）而非修改实现 |
| 符合单一职责原则 | 相关操作集中在一个 `Visitor` 中，而非分散在各个 `Element` 类里 |
| 操作集中管理 | 同一类操作（如序列化、导出）集中在一个 `Visitor` 类中，便于维护 |
| 支持累积状态 | `Visitor` 可以在遍历过程中积累状态（如计算总面积） |

### 缺点

| 缺点 | 说明 |
|------|------|
| **Element 类层次结构必须稳定** | 这是最大的限制。如果新增一个 `ElementC` 子类，`Visitor` 基类必须修改，违背了模式的前提 |
| 扩展 Element 子类困难 | 每新增一个具体元素类，所有 `Visitor` 子类都要修改 |
| 增加了类的数量 | 每个新操作对应一个 `ConcreteVisitor` 类 |
| 破坏封装 | `Visitor` 可能需要访问 `Element` 的内部状态，可能需要暴露 `public` 接口 |

## 七、适用场景

Visitor 模式适用于以下条件**同时满足**的场景：

1. **Element 类层次结构稳定**：基类有多少个子类是确定的，不会再增加新的子类
2. **操作频繁变化**：需要经常为整个类层次结构添加新的操作

### 两种极端情况

- **如果 Element 类层次结构不稳定**：Visitor 模式不适用，因为新增子类就要改 Visitor 基类
- **如果操作不需要频繁改动**：不需要用 Visitor 模式，直接在 Element 中设计好所有操作即可

### 设计模式的核心艺术

> 设计模式的要点是能够判断其中的**稳定点**和**变化点**。如果判断出错，后续的设计模式应用就是错误的。
>
> - 所有东西都稳定 → 不需要设计模式
> - 所有东西都变化 → 任何模式都解决不了
> - **常态**：有稳定的部分，有变化的部分

---

## 八、总结

| 要点 | 说明 |
|------|------|
| 模式本质 | 通过 Double Dispatch，在不修改 Element 类层次结构的前提下，动态添加新操作 |
| 核心机制 | `element.accept(visitor)` 触发两次虚函数调用：第一次根据 element 类型分发，第二次根据 visitor 类型分发 |
| 最大优点 | 遵循开闭原则，新增操作无需修改已有代码 |
| 最大缺点 | Element 类层次结构必须稳定（子类个数确定），否则模式失效 |
| 适用场景 | Element 类层次结构稳定，但操作需要频繁变化 |
| 使用频率 | 前提条件苛刻，一般不常用；但一旦使用，整个类层次结构都会被 Visitor 所影响（"用得很重"） |
